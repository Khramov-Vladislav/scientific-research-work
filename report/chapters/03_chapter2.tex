Такой широкий временной диапазон существенно затрудняет непосредственное

$43.2$~секунды). Такой масштаб оптимален для оперативной и наглядной практической 
демонстрации динамики заполнения очередей диспетчера SLURM в реальном времени непосредственно 
в процессе защиты работы.

\subsubsection{Выбор модели ошибки оценки времени выполнения}

Для характеристики отклонения пользовательской оценки времени
выполнения от фактического времени выполнения задачи использовались
две альтернативные модели:
\begin{itemize}
\item абсолютное отклонение $\Delta T = T_{\text{заявки}} - T_{\text{факт}}$;
\item относительное отклонение $\tau = T_{\text{заявки}} / T_{\text{факт}}$.
\end{itemize}

\subsubsection{Алгоритм генерации пользовательской заявки}

Генерация каждой синтетической заявки выполняется программно на языке Python и состоит из нескольких ключевых этапов, базирующихся на статистических параметрах исходного датасета.

На первом этапе фактическое время выполнения задачи $T_{\text{факт}}$ моделируется как случайная величина, подчинённая нормальному распределению $\mathcal{N}(\mu_t, \sigma_t^2)$. Математическое ожидание и стандартное отклонение задаются на основе масштабированных границ исследуемой выборки:
\[
\mu_t = \frac{T_{\text{min}} + T_{\text{max}}}{2}, \qquad \sigma_t = \frac{T_{\text{max}} - T_{\text{min}}}{4}
\]
Данный выбор параметров обеспечивает попадание более 95\% генерируемых значений в требуемый диапазон $[T_{\text{min}},\, T_{\text{max}}]$, где $T_{\text{min}} = 1$~с, а $T_{\text{max}} = 43$~с. Программная реализация осуществляет генерацию в цикле до тех пор, пока значение не удовлетворит критерию $T_{\text{min}} \le T_{\text{факт}} \le T_{\text{max}}$. Полученное время $T_{\text{факт}}$ округляется до целого числа секунд и используется в качестве параметра команды \texttt{sleep} в теле формируемого пакетного сценария.

На втором этапе пользовательская оценка времени выполнения задачи $T_{\text{заявки}}$ вычисляется как:
\[
T_{\text{заявки}} = \text{round}(T_{\text{факт}} \cdot \tau), \qquad \tau \sim \mathcal{N}_{\text{log}}(\mu, \sigma^2),
\]
то есть отклонение оценки от фактического времени (величина человеческой ошибки $\tau$) моделируется логнормальным распределением с вычисленными параметрами $\mu = 3.8621$ и $\sigma = 0.8489$. Программно заложена защита от некорректных значений: если сгенерированная оценка времени оказывается меньше или равна фактическому времени ($T_{\text{заявки}} \le T_{\text{факт}}$), лимит принудительно корректируется добавлением случайного интервала от 5 до 15 секунд. Это исключает преждевременное прерывание задачи демоном \texttt{slurmctld}.

Количество узлов, запрашиваемых заявкой, выбирается случайным образом из дискретного множества $\{1, 2, 3, 4\}$ с использованием \textbf{равномерного распределения} посредством встроенной функции \texttt{random.choice()}, независимо от количества узлов, фигурирующего в исходных данных по варианту.

При отправке задачи в очередь SLURM вычисленное значение $T_{\text{заявки}}$ в секундах транслируется в формат временного лимита диспетчера \texttt{--time} (\texttt{ММ:СС}) с округлением в большую сторону до ближайшей минуты (минимум 1 минута), что гарантирует стабильность работы планировщика на коротких интервалах времени.

\subsubsection{Реализация программы-имитатора}

Имитатор реализован на языке \texttt{Python 3} и принимает в качестве входного параметра командной строки количество генерируемых заявок $N$ (целое положительное число в диапазоне от 1 до 999). Для каждой из $N$ заявок программа выполняет следующий цикл действий:
\begin{enumerate}
\item генерирует значения $T_{\text{факт}}$, $T_{\text{заявки}}$ и количество вычислительных узлов согласно описанным математическим распределениям;
\item формирует динамический пакетный сценарий SLURM с жестко заданным именем задачи \texttt{run\_bwa.sh}, указанием необходимого количества узлов (\texttt{--nodes}), вычисленного и отформатированного предельного времени выполнения (\texttt{--time}) и системной командой \texttt{sleep} с аргументом $T_{\text{факт}}$ в качестве имитации вычислительной нагрузки;
\item автоматически отправляет сформированный сценарий в очередь планировщика посредством вызова системной утилиты \texttt{sbatch} через модуль \texttt{subprocess}, перехватывая назначенный сервером \texttt{SlurmJobID};
\item осуществляет логирование метаданных (временная метка, внутренний ID, ID в системе SLURM, количество узлов, плановое и фактическое время, а также коэффициент ошибки $\tau$) в файл статистики \texttt{/home/vlad/simulation\_stats.csv} для последующего анализа;
\item производит автоматическую очистку рабочей директории, удаляя временный файл сценария сразу после его постановки в очередь.
\end{enumerate}

\subsubsection{Сбор статистики поставленных в очередь заявок}

Для последующего анализа и сравнения теоретических (плановых) параметров с фактическими системными характеристиками выполненных задач, сбор статистики осуществлялся параллельно двумя методами:
\begin{enumerate}
\item \textbf{Программное логирование:} скрипт-имитатор \texttt{simulator.py} в момент генерации фиксировал внутренние параметры распределений и расчетные значения в файл \texttt{simulation\_stats.csv}.
\item \textbf{Системный аудит SLURM:} сбор метрик планировщика выполнялся утилитой \texttt{sacct}. Из базы данных подсистемы учета извлекались идентификатор задачи (\texttt{JobID}), имя (\texttt{JobName}), количество выделенных узлов (\texttt{Nodes}), финальное состояние (\texttt{State}) и точное астрономическое время выполнения (\texttt{ElapsedRaw}).
\end{enumerate}

Результаты системного сбора экспортировались в текстовый файл \texttt{slurm\_real\_fact.txt} с использованием разделителя \texttt{|} для последующего сопоставления с логом имитатора.
